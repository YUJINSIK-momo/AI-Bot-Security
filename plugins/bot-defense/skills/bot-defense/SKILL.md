# 봇 방어 — 전체 흐름

## 원칙 (늘 지킨다)

1. **내 서비스만.** 사용자가 소유하거나 점검 권한이 있는 사이트 · 계정에만 쓴다. 확실하지 않으면 묻는다. 남의 사이트를 탐색하거나 방어를 비켜 가는 데 쓰지 않는다.
2. **읽기만.** 클라우드 · DNS · CDN · 배포를 바꾸지 않는다. 바꿀 것은 코드 · IaC 변경안(PR)이나 체크리스트로 내고, 적용은 사람이 한다. 이 플러그인의 훅은 바꾸는 명령을 만나면 사용자에게 묻는다.
3. **비밀을 다루지 않는다.** 키 · 토큰을 대화에 붙여 달라고 하지 않는다. 로그인은 사용자가 자기 터미널에서 한다. 출력에 키 값 · IP 원문 · 계정 ID 전체를 쓰지 않는다.
4. **보고서는 약점 목록이다.** 공개 저장소 · 공개 채널에 올리지 않는다. 저장 위치는 묻는다(`references/config.md` 의 `report_dir`).
5. **완전히 막을 수 없다는 것을 숨기지 않는다.** 목표는 넷이다: 대량 복제를 느리고 비싸게, 비용이 새는 길 차단, 탐지, 다툴 근거.
6. **그 팀의 규칙이 먼저다.** 소비 저장소의 CLAUDE.md · 변경 기록 규칙(`.bot-defense.json` 의 `change_policy`)을 따른다.

## 순서

1. **범위를 정한다.** 대상 저장소, 운영 주소, 클라우드 계정(있으면). 값은 `references/config.md` 의 순서로 찾고, 없으면 묻는다. 운영 주소가 사용자 것인지 확인받는다.
2. **스택을 판별한다.** `stack-detect` 스킬(`/bot-defense:stack-detect`).
3. **노출을 점검한다.** `exposure-audit` 스킬. 코드의 공개 경로와 운영 사이트를 공격자 시점으로 본다.
4. **호스팅별로 본다.** 2의 결과에 나온 `playbooks` 문서를 읽는다(`${CLAUDE_PLUGIN_ROOT}/references/...`).
   - AWS 면 `aws-bot-defense` 스킬로 계정을 읽기 전용으로 본다.
5. **위협과 대응을 맞춘다.** `${CLAUDE_PLUGIN_ROOT}/references/threats.md` 의 위협 T1 ~ T6 × 층 표로, 이 서비스에서 실제로 열린 것만 고른다.
6. **보고서를 쓴다.** `${CLAUDE_PLUGIN_ROOT}/references/report-template.md` 형식. 대응은 싼 것부터, 각 대응마다 「막는 위협 · 비용 · 누가 정하나 · 바꾸는 곳」을 적는다.
7. **(선택) 감시를 붙인다.** `log-watch` 스킬로 지금 로그를 보고, 상시 감시(경보)를 제안한다.

## 대응을 고를 때의 기본 순서

1. 규칙: robots.txt, 약관 조항(문구는 기획 · 법무가 정한다 — 초안만)
2. 앱: 비싼 경로(LLM · 유료 API)의 「새로 만들 때만」 상한, 공개 데이터 경로의 IP 상한(처음엔 세기만)
3. 앞단: WAF · CDN 의 봇 규칙과 속도 규칙(처음엔 Count)
4. 설계: 값진 데이터를 로그인 뒤로(서버에서), 브라우저 확인(Challenge · 토큰)
5. 증거: 복제 증명용 표식(기획 결정)

하지 않을 것도 적는다: JS 난독화, 개발자 도구 감지, 우클릭 막기.

## 결과로 남기는 것

- 보고서(위 형식) — 사용자가 고른 곳에
- 바로 할 수 있는 변경은 PR 초안(그 저장소의 커밋 · PR 규칙대로). 머지 · 적용은 사람이 한다.
- 결정이 필요한 것 목록(기획 · 법무 · 비용)
